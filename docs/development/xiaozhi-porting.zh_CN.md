# 小智（xiaozhi）语音对话移植：设计、内存攻坚与调试复盘

> 说明：本文是 `o-platform` **移植探索小智 AI 对话链路**的聚合技术记录，合并自原
> 「音频管线设计 / 进度交接 / WebSocket 调试复盘」三份文档，并**剔除了设备标识、网络/密钥、
> 本机路径等不宜公开的内容**，只保留对后续移植有复用价值的结论。
>
> **结论先行：** 该路线（进页面 → 连小智官方 WebSocket → 端侧 Opus 编解码 → 服务器对话/TTS）
> 在无 PSRAM 的 ESP32-C3 上**最终被放弃**，改为现在的**轻量 ADPCM 语音输入**架构（见
> `components/passport_voice`）。放弃的根本原因是**内存**：小智全链路常驻所需连续堆
> （证书 bundle + Opus 编解码器 + 任务栈）与 BLE/Wi‑Fi/工牌 UI 抢不下。**但它踩出来的内存
> 预算经验与调试纪律非常值钱，故单独成文，供以后任何"再移植一个语音/网络功能"时参考。**

关联：`docs/development/porting-pipeline.zh_CN.md`（移植总则）、README「内存 / 栈工程」一节。

## 1. 目标与 donor

- donor：本板官方定制小智固件（基于 `78/xiaozhi-esp32`），**同款 ESP32-C3、同样无 PSRAM**。
- 原则：**所有行为参数以 donor 在本板的实际运行为准**，不从上游通用代码推断、不自己发明。
- 目标：进页面 → 按键对话 → 语音上行 → AI TTS 播放，一次打通。

关键参数（源自 donor）：16kHz / 单声道 / Opus 60ms 帧 / complexity=0 / VBR / DTX；I2S 24kHz；
上行协议 v3 二进制帧 `type(1B)+reserved(1B)+payload_size(2B 大端)+payload`；Opus 用
`espressif/esp_audio_codec`；唤醒词/AEC/VAD 在 C3 上本就不可用（donor 出厂即关），不移植。

## 2. 音频管线架构

```
上行: MIC(24k I2S) → input 任务(10ms 读) → 重采样24k→16k → 60ms 组帧
      → 编码队列(≤2) → opus 任务(编码) → 发送队列(≤40) → send 任务 → WS
下行: WS 二进制帧 → 解码队列(≤20) → opus 任务(解码 + 重采样16k→24k)
      → 播放队列(≤2) → output 任务 → bsp_audio_write(阻塞写=自然节流)
```

**内存模型（最重要的结论）：照抄 donor 的行为与队列上限，不照抄"内存够用"的假设。**
- 队列用**逐包动态分配**，不用静态预分配环——静态预分配内存不够时**硬崩**；动态分配不够时
  `malloc` 返回 NULL → **丢这一帧 + 打日志**、对话继续、仅抖动缓冲变小。未知占用被自动压成
  音质降级而非崩溃。
- 队列上限（40/20）是**天花板**不是内存承诺，平时接近空；曾因"基线比 donor 低"把上限裁到 16/12/3
  是**错的**（裁的是 donor 验证过的抗抖动窗口，对低基线毫无帮助——低基线时队列本就到不了 40）。

**必须盯的硬承诺（真正的常驻开销）：** opus 任务栈、input/output 任务栈、Opus 编码器状态
(~17KB)、解码器状态(~13KB，与编码器错峰不同时在)、I2S DMA、重采样器 ×2、以及 ——**证书 bundle**。

## 3. 内存攻坚（本路线最终死于此处，经验最贵）

按时间顺序、由浅入深，四条确定性教训：

1. **TLS 根证书 bundle 常驻吃 ~65KB。** `esp_crt_bundle` 会把上百张 CA 在运行时整包解析进堆并
   常驻，直接挤掉 Opus 编码器需要的 17KB 连续块 → `OPUS_ALLOC_FAIL(-7)` → 上行全哑。
   应对：**只信任目标站点的少数自签根 CA**（内嵌精简 PEM），净省 ~65KB；代价是以后新增 HTTPS
   域名须手工补根，否则静默握手失败。
2. **任务栈 HWM 读反 → 爆栈崩溃。** ESP-IDF 打印的是**已用字节**不是剩余；且在编码路径未真正跑过时
   采样值偏低无效。据此误把 opus 栈裁到 8192 → 编码路径 `Stack protection fault`。教训：
   **栈 HWM 是"已用"，且必须在代码路径真跑过之后再采样**；栈不能乱砍（栈溢出比堆紧张更糟）。
3. **大栈必须先于编解码器分配（建栈顺序）。** 初始化里应**先建 opus 大栈任务**（趁最大连续块还在）
   → 再开编码器/解码器 → 最后建小栈任务；反了会因编解码器切碎堆而 `opus 建栈失败`。
4. **开机自启 + Wi‑Fi 常驻 = 堆不足。** 自启让 Wi‑Fi 常驻 ~99KB，进页面音频 init 时最大连续块
   不够装 opus栈+编解码器 → 反复 `ret:-7`/无声。**最终决定放弃自启**：Wi‑Fi 只为开机 SNTP 校时、
   完成/超时即释放；对话改为按需进页面触发。后续又做了四项确定性优化（opus 栈按实测 HWM 缩减、
   WS 发送任务栈修正爆栈、解码器延迟到首包创建、Wi‑Fi 管理缓冲动态化 + 关企业级 Wi‑Fi），
   把 init 音频需求从 ~51KB 降到 ~33KB。

> 这套内存方法论**直接迁移到了现在的 ADPCM 语音架构**：单一共享 NimBLE 栈、Wi‑Fi 不常驻、
> 零堆静态缓冲 + `event_worker` 任务栈放 `.bss`（详见 README「内存 / 栈工程」）。

## 4. WebSocket 调试复盘（通用纪律，最可复用）

现象：WS 101 握手成功 → 收到服务器 hello → 立即被 `CLOSE`。

**真因（固件侧，一个静默失败）：** 在 `esp_websocket_client_start()` **之前**调用
`esp_websocket_client_set_headers()` 且**忽略返回值** → 该 API 内部
`if (state != CONNECTED) return ESP_ERR_INVALID_ARG` → 鉴权头（Device-Id / Client-Id / Authorization /
Protocol-Version）根本没进握手 → 服务器认不出设备、hello 后 CLOSE。101 只是 HTTP upgrade 放行，
不等于鉴权通过。

**绕过的弯路（都是"症状外指 + 假设锚定"）：** 误判"服务器对 test 设备死态""BLE 干扰""组件生命周期"
——全不是。把 `unexpected data readable`（其实是**结果**：客户端先决定关闭、残留帧没被读）当成原因。

**一次性破案的两招（不依赖任何参考）：** ① 读 esp-idf 自己那行 API 源码约束；② PC 端最小 A/B
（同 URL/token，只差一组头）——不带头即复现"101 后被关"，带头则连接保持。

## 5. 给后续移植的可执行 Checklist

- 第三方库 API 静默失败 → **先 grep 读它的源码约束**（state/调用时机/是否需已连接）；esp-idf 的约束
  常藏在**返回值**里，**任何返回值都要查**（`ESP_ERR_INVALID_ARG`/`ESP_FAIL` 出现即信号）。
- 异常先做**最小 A/B 隔离**（只改一个变量），一次把「客户端 vs 服务器」「本模块 vs 其它」切开。
- 网络问题**先 dump 自己发出去的报文**，别盯着收到的响应找锅；分清日志因果（谁先关的）。
- 不锚定早期假设（名字带 test、日志带某关键词，都不构成结论）。
- 实现 RPC/协议先区分**请求（需回复）vs 通知（单向）**（前缀/有无 id）。
- 栈按**已用 HWM** 在代码路径跑过后定容，别凭猜；大栈先分配、再开编解码器。
- 内存不够时优先**优雅降级（丢帧不崩）**，别用静态预分配把自己逼成硬崩。
